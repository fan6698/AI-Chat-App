## 打字机节流（性能专项）
- 新增 `src/utils/deltaBuffer.ts`：纯逻辑无 React 依赖，可独立单测。`push` 合并 delta，`dispose` 冲刷残余 + 清定时器。
- 两层设计：间隔窗口内的 token 合并为一次刷新；**超过间隔后的第一个 token 同步立即 flush**，保证首字不等帧（否则首个字要等一个间隔才出现，体感变差）。
- 关键补充：`ChatMessage` 用 `memo` 包裹。原先每次 setState 都会让整棵消息列表重渲染，所有历史消息的 Markdown 被反复重新解析——长对话下这个开销比逐 token 渲染还大。加了 memo 后只有最后一条 AI 消息会重建。
- 每请求一份缓冲区（在 handleSend 里创建），避免"流式进行中清空对话 → 旧请求残余文本串进新回答"的竞态。
- 新增 `scripts/verify-delta-buffer.mjs`，7 项全过：密集合并（300 token → 2 次刷新：首字 1 次 + dispose 残余 1 次）、首字立即上屏、持续流式的刷新次数只与时长相关而非 token 数、dispose 冲刷残余、无定时器泄漏、顺序完整性、空 token 不刷新。
- 踩坑：断言里写死刷新次数会受 Windows 定时器粒度（~10ms 精度）影响而误判，改为按实际 elapsed 计算期望上限。
- 校验：31 项测试全通过（api 9 / storage 9 / markdown 6 / streaming 7）；build + oxlint 全绿（18 文件）。
- 仍待真实环境验证：渲染 FPS 改善程度需浏览器实测（需先配 API Key）。

- `src/api.ts` 改为双模式：**以 `VITE_ZHIPU_API_KEY` 是否为空自动切换**。直连带 Bearer 且传 model；代理模式只发 `{messages, model}`，不带任何鉴权头。前端解析逻辑完全复用。
- 前端类型：`vite-env.d.ts` 里 VITE_ZHIPU_API_KEY 改为可选，新增 VITE_CHAT_ENDPOINT。`api/**/*.ts` 加入 tsconfig.node.json。
- 新增 `scripts/verify-proxy.mjs`（6 项）：405 / 500 缺 Key / 8 种非法入参拦截 / 正常转发且 Bearer 来自服务端 / 上游 401 透传 / 上游不可达 502。
- **同步修了一个假绿灯**：verify-api 第 8 项原断言"无 Key 就报错"，改成代理模式后行为变了，必须改断言（否则测试通过但行为是错的）。同时修了 fetch mock 在测试 7 被替换后未还原、污染后续用例的问题。
- **又抓到一个真 bug**：`deltaBuffer` 首字立即刷新原先靠 `performance.now() - lastFlushAt(初值0)` 判断，时间原点依赖运行环境，进程刚启动时可能还没超过间隔 → 首字被延迟。改为 `lastFlushAt: number | null` 显式判断"是否刷新过"。这个 bug 是跑聚合 verify 时才暴露的——说明聚合跑全量有必要。
- 安全实测（关键证据）：直连构建 `dist/assets/*.js` 能 grep 到真实 Key（命中 1 个文件）；用空 envDir 的部署模式构建命中 0 个文件，且正确引用 `/api/chat`。
- 校验：37 项全通过（api 9 / storage 9 / markdown 6 / streaming 7 / proxy 6）；build + oxlint 全绿（20 文件）。
